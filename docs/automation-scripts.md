# 自動化腳本 設計

狀態:**設計定案 + 可行性已驗證,尚未動工**(2026-07-28)
目標讀者:本專案維護者

## 可行性驗證(2026-07-28,丟棄式 spike)

- **OpenCV.js `matchTemplate`(最大未知)✅**:`@techstark/opencv-js`(WASM,無原生編譯)在 Node 載入 OK。`TM_CCOEFF_NORMED` 模糊比對——模板加「亮度 +40、雜訊 ±25」仍相似度 **0.992**,不存在時 **0.000**(門檻乾淨分辨)。效能:1080×2400 全幀 **~68ms**、縮 50% **~11ms**;因 `screencap`(~200–500ms)才是瓶頸,比對成本幾乎可略。**`cv.imdecode` 可直接解 screencap 的 PNG → Mat**(免另外 PNG 解碼庫)。
- **`screencap` / `adb shell input`(真機 XQ-AS72 實測)✅**:`exec-out screencap -p` → PNG 約 **0.32–0.45s**;`input tap` 暖機後 **~70ms**、`swipe` ~0.42s、`keyevent` ~0.09s。座標空間 = **邏輯解析度(= screencap 尺寸 = input 座標)**;此機 `wm size` 為 Physical 1080×2520 / Override 1080×1920,screencap 就是 1080×1920。
- **螢幕必須喚醒才有畫面(spike 抓到的關鍵細節)**:睡眠中 screencap 是全黑(~12KB);`input keyevent 224`(WAKEUP)喚醒後 screencap 才有真實內容(~515KB)。→ **引擎執行前要先喚醒顯示**,鎖屏無 PIN 時**上滑解鎖**(有 PIN 則無法,需使用者自理)。可能還要在腳本執行期間維持喚醒(wakelock / `svc power stayon` / 關屏 keeper 的合成保活)。
- 結論:全綠。視覺堆疊 = **喚醒 → screencap → cv.imdecode → matchTemplate(TM_CCOEFF_NORMED,可縮放加速)→ input**;單圈約 screencap(~350ms)+ 比對(~11–68ms)+ 動作(~70ms)≈ 每秒約 2 次。

## 目標

在 UI 上編輯、儲存、執行「視覺自動化腳本」——依**座標顏色**或**圖像模糊比對**做點擊/滑動,支援迴圈與條件,可**排程定時**執行並依**優先權搶佔**。典型用途:遊戲掛機/農場、每日定時活動、簽到。

## 架構決策

- **引擎跑在伺服器端,完全用 adb,獨立於瀏覽器/scrcpy session**:
  - 視覺 = `adb screencap`(已有縮圖那套基礎;螢幕關著也能抓)。
  - 動作 = `adb shell input tap/swipe/text` + `input keyevent`。
  - → 裝置上**沒開任何 viewer session 也能跑腳本**,真正「擺著跑」。
- **每台裝置同一時間只跑一支腳本**(見〈排程與優先權〉);以背景任務執行。
- 瀏覽器 UI 只負責**編輯 + 取值 + 啟停 + 看狀態/log**。

## 座標與視覺

- **座標一律正規化(0–1)**:換解析度(見 `docs/*`/解析度覆寫功能)、旋轉都不會壞;執行時用當下 `wm size` 換算像素。
- **色彩比對**:某正規化點的 RGB 與目標色比,帶**容差**(%);用來做「等待顏色 / 若顏色」。
- **圖像比對(主力)**:**OpenCV.js(WASM,無原生編譯、Docker 友善)** `matchTemplate` + `TM_CCOEFF_NORMED` → 得最佳位置 + **相似度分數(0–100%)**;超過使用者設的**相似度門檻**就點它的中心(可加偏移量)。
  - 「模糊」= 相似度門檻(容許亮度/小差異)。
  - 可限**搜尋區域**加速。
  - **限制**:template matching **不抗縮放**——模板綁「擷取時的解析度」;跨解析度可能失準。對策:模板記錄擷取解析度、必要時做**多尺度比對**(階段三,略吃 CPU)。尺度/旋轉全免疫的特徵比對(SIFT/ORB)更重,MVP 不做。
  - 視覺頻率受 `screencap` 限制(每張約 200–500ms)→ 約每秒 2–5 次判斷;適合掛機/回合制,不適合快節奏。
- 影像處理堆疊:screencap PNG 解碼(pngjs / sharp)→ 像素 → OpenCV.js 比對。
- **文字比對(OCR)**:**PP-OCRv6-small(ONNX,以 `@gutenye/ocr-node` 當推論殼)**。實測在遊戲美術字型上明顯勝過 Tesseract:同一顆 4 字按鈕 Tesseract 怎麼前處理都只讀出 3–4 字中的一部分,PP-OCR 一次讀對;且暗底低對比不需要額外正規化。用於「依文字點擊 / 若文字含 / 讀取數值」。
  - 比對是**忽略空白的子字串**比對——美術字型偶爾會吃掉或換掉一兩個字,所以找**有辨識度的片段**而不是整串標籤。
  - **強烈建議框選區域**:整張畫面約 1.7–2.5s,框一小塊約 50ms(差 ~30 倍)。

#### 為什麼不用套件內建的模型

`@gutenye/ocr-node` 綁的是 **PP-OCRv4**,字典 `ppocr_keys_v1.txt` 只有 6623 字、且是簡體取向 —— **遊 戲 戰 獎 勵 閉 認 擇 擊 儲 繼 簽 領 螢 錢 尋 閒 闖** 這些日常繁體字根本不在字典裡,模型不管圖多清楚都輸出不了。真機實測:`策略遊戲·塔防遊戲` 被讀成 `策略游·塔防游`(戲整個消失)、`數獨闖關大挑戰` 讀成 `數獨關大挑`。這對繁中介面的自動化是致命的。

改用官方 **PP-OCRv6-small ONNX**(det 9.4MB + rec 20.2MB,字典 18708 字)後,上述全部正確。代價是單區域辨識 34ms → 46ms(+35%),相對 `screencap` 本身的 ~350ms 是雜訊。

模型由 `packages/server/scripts/fetch-ocr-models.mjs` 在 **postinstall** 下載(比照 `scrcpy-server.jar` 的做法),附 SHA-256 驗證,不進 git;下載失敗時退回內建 v4 並在 log 警告,離線開發仍可用。

⚠️ **不要用 v6-tiny** —— 它的字典只有 6904 字,繁體缺口跟 v4 幾乎一樣。

#### 簡繁摺疊

即使字典補齊了,PP-OCRv6 **同一段像素在不同裁切下會吐出不同字形**:整張畫面讀成 `已安裝`,裁窄後同一顆按鈕讀成 `已安装`。這不只讓使用者搜不到,還會打斷引擎自己的收窄流程(收窄就是拿整行去比對它自己的裁切)。

所以比對一律先過 `scriptTextKey()`:**摺疊成單一字形 + 去空白 + 轉小寫**。對照表由 `packages/shared/scripts/build-han-fold.mjs` 從 OpenCC 的 `TSCharacters.txt` 產生(3222 組)進 repo,執行期零相依 —— `opencc-js` 有 5.9MB,絕大部分是字元級比對用不到的詞組/地區慣用語資料。附帶好處:使用者打簡體或繁體都找得到。

(產表時注意:表裡有 BMP 以外的字,必須用 code point 迭代而非 `str[i]`,否則整條對照從第一個代理對之後全部錯位。)

### 點擊座標:為什麼要「收窄」

PP-OCR 把**同一條水平帶**視為一行:app 圖示、評分、標籤常常被合併成同一個框。所以「行的中心」經常根本不在你要點的字上——實測 `Sudoku without ads` 這一行,行中心 x=335,而 `without` 實際在 **x=459**,差 124px,必定點錯。

先前用「字寬估算」(依 CJK/半形推算子字串在框內的比例)推位置,**在最需要它的時候會壞**:框寬包含了圖示這類**不對應任何字元的像素**,估算前提直接不成立(實測偏離目標字 28px,落在字外)。

因此改成**實際去量**(`packages/server/src/scripts/ocr.ts` 的 `refine`):把那條帶**水平二分**(兩半重疊 15%,讓壓在接縫上的字仍能完整落在某一側),各跑一次 OCR,保留仍然含有目標字的那半,重複到框住的就是目標字本身。只切水平、垂直範圍固定沿用原行(每輪重裁垂直會逐步吃掉上下延伸筆畫,文字會變得認不出來)。

- 成本:額外 **4–6 次小裁切 OCR,約 +10–260ms**(相對整張畫面本身就要 ~1.8s)。
- 上限是**每一符合行 16 次**,不是整次辨識共用一池。共用池會讓各行互相耦合:前幾行花光後,後面的行只能回報整條帶,於是「畫面上有幾個符合」會取決於剛好有多少別的行也符合 —— 存好的 `occurrence: 3` 就可能哪天指到別的地方。實測共用池 24 → 48 時,同一張畫面的候選數從 4 變 3。每行獨立後,16/20/28 三種設定的候選數完全一致。
- 另有「最多收窄前 8 行」的上限;超過的行直接回報整條帶。框選區域從不會碰到這個上限,整張畫面搜常用詞才會 —— 那正是建議框選區域的理由。
- 這件事**只在伺服器算一次**,`tapText` 與編輯器的「測試預覽」共用同一個 `tap` 結果 → 預覽畫的十字**保證**就是引擎會點的點。

### 找到之後:過濾 → 數量檢查 → 排序 → 取一個

一個視覺步驟找到的東西要經過四段才會被點:

| 段 | 做什麼 | 設定 |
|---|---|---|
| **過濾** | 哪些算數 | `filter.mode`(包含/前後無字/整行相符)、`filter.color` + 容差、`filter.minHeight`/`maxHeight`、`filter.minConfidence`、`region` |
| **數量檢查** | 數量不如預期就當作還沒好 | `pick.expect`(任意 / 必須剛好 1 個) |
| **排序** | 用什麼順序數 | `pick.by`(由上而下/最左/最右/最上/最下/最像/**離參考點最近或最遠**/隨機) |
| **取一個** | 第幾個 | `pick.index` |

`mode` 判定在**整行**上,不是收窄後的框 —— 收窄的結果本來就只有目標字,前後有什麼只有整行知道。`standalone` 的規則是「等於整行以空白切出的某一個完整 token」;OCR 漏掉空白時整行變一個 token,規則退化成 `exact`,**保守方向**(寧可不匹配也不誤匹配)。

`expect: "one"` 就是「預期只有一個,多個代表誤判」的解法:數量 ≠ 1 時當作還沒找到,靠既有的輪詢繼續等,過場畫面通常一兩幀就穩定。

`random` 的執行紀錄一定會寫出它取到第幾個,否則事後無從追查。

#### 顏色過濾

文字加顏色的鑑別力遠大於文字本身:啟用/停用的按鈕字面一樣、稀有度只差顏色。真機實測(遊戲載入畫面),同一個 `%` 出現兩次:

| 讀到 | 擷取到的文字色 |
|---|---|
| `100%`(進度細節) | `#a7a8b1` 灰 |
| `5%`(來自 75%) | `#5bc760` 綠 |

**怎麼取「文字的顏色」**:緊貼字的框裡,出現最多的顏色是**背景**,離背景夠遠(RGB 距離 ≥ 60)之中出現最多的就是**文字**。再用該群的實際像素平均,而不是量化桶的中心 —— 桶中心每個通道可能差到 8 階,比較兩種灰時看得出來。

這只在「收窄之後」成立 —— 對整條辨識帶做同樣的事,同一列的圖示會蓋過文字。

**取色方式**:候選清單每一列都顯示它偵測到的文字色色塊,**點一下就採用為條件**。不要求使用者去猜十六進位。容差是 RGB 距離的百分比,預設 15%。

**限制**:漸層字、描邊字沒有單一顏色,容差再大也不穩,那種情況應該改用找圖。

#### 距離排序的參考點

「離參考點最近」用於「距離角色最近的怪物」這類需求。參考點是**正規化固定座標,預設畫面中心** —— 鏡頭鎖定角色的遊戲(ARPG、俯視角、塔防)角色永遠在畫面同一位置,通常就是正中央,所以多數情況預設值直接可用。編輯器可以在畫面上點選改設,並畫出參考點與到中選目標的連線,否則「最近」無從確認。

**限制**:固定點只在「被測量的對象不會在畫面上移動」時成立。要從會動的東西測距,需要先有步驟把它找出來並記住位置 —— 完整解是變數(階段三),輕量解是一個「設定參考點」步驟。`refX`/`refY` 兩個欄位屆時不用改,只是多一個來源選項。

**距離必須用像素算,不能用正規化座標** —— 1080×1920 上正規化的 0.1 橫向是 108px、縱向是 192px,直接在正規化空間量歐氏距離會嚴重低估縱向權重,「最近」會挑錯。`scriptSelect` 因此需要傳入畫面尺寸。

**全部集中在 `shared` 的 `scriptSelect()`** —— 引擎和編輯器預覽呼叫同一支純函式。這是防止「預覽說 A、執行點 B」的唯一方法,而那正是這個功能開發過程中真正踩到的 bug。

因為是純函式,探測 API 回傳的是**未過濾**的候選 + 屬性(整行文字、信心度),過濾在前端即時算:拖信心度滑桿、切比對方式,框和編號立刻重排,**不用重抓畫面**(實測同一次探測的 `4307ms` 在三種設定下都不變)。只有改「範圍」需要重新探測。

### 多個符合時選哪一個

畫面上同時有好幾個符合是常態(一排一樣的按鈕、`已安裝` 與 `解除安裝` 同時在)。原本兩條路徑都是**隱式挑一個**——文字取「最窄的符合行」、找圖取 `minMaxLoc` 的最高分——實測會選錯(搜 `ads` 選到左邊圖示上的 `ADS` 徽章而不是標題),而且使用者無從得知有別的候選。

改成三件事:

1. **明確的順序**:所有候選一律照**閱讀順序**排(由上而下;垂直中心相差不到半個行高視為同一列,列內由左而右)。這是使用者看著畫面就能自己數出來的順序。
2. **步驟上的 `occurrence`**(`tapText` / `findTap`,預設 0 = 第一個)。`ifText` / `ifImage` 只問「有沒有」,不需要。
3. **測試預覽把候選全部編號畫出來**,點編號就換選,並寫明「畫面上有 N 個符合,目前會點第 K 個」。選擇是純前端的,不會重跑一次擷取+辨識。

實作:
- 文字:`refine` 遞迴**兩半都進**(而不是只走比較好的那半),因此同一條帶裡重複出現的字也會全部被找出來;重疊的框視為同一個(重疊 > 較窄者的一半)後去重。
- 找圖:對 `matchTemplate` 的分數圖做**反覆取峰值**的 non-maximum suppression——取全域最大、把模板大小的鄰域抹掉、再取下一個,上限 12 個。比起把所有超過門檻的格子都收集起來再排序,記憶體便宜得多。
- 執行紀錄會寫 `(2 個中的第 1 個)`,只有真的不只一個時才寫。

## 取值 UX(核心)

每個座標/顏色/模板參數旁有「拾取」鈕:
- **座標/顏色**:按下 → 伺服器抓一張 screencap 疊上來 → 點一下畫面 → 存**正規化 (x,y) + 該點顏色**。
- **模板**:按下 → 在 screencap 上**框選矩形** → 存成模板(base64 PNG + 擷取時解析度)。

## 排程與優先權搶佔

- 每支腳本有:
  - **觸發**:`手動` / `常駐`(持續跑,搶佔後自動恢復)/ `排程`(每日 HH:MM、間隔、特定時間)。
  - **優先權**(整數;或 高/中/低)。
- **每台裝置永遠跑「當下最高優先的『啟用中』腳本」**:
  - `常駐` = 一直啟用(直到手動停)。`排程` = 到點啟用、**跑完**(有限)後停用到下次。`手動` = 按執行到跑完/停。
  - 優先序:**人為手動操作 > 排程腳本 > 常駐腳本**。
  - **搶佔**:更高優先者啟用(排程到點 / 你手動接手)→ 當前者暫停;高優先者**跑完 / 你放手**後,裝置自動**落回下一個最高的啟用腳本**(常駐就這樣恢復)。
  - **恢復 = 從頭重跑**(遊戲狀態已變,從中間接續危險)。
  - **前提**:搶佔者必須是**有限、會結束**的(定時活動跑完就結束),否則常駐永遠回不來。
- **時區**:排程用伺服器時鐘 +（可設）時區。

## 腳本模型(JSON)

```
Script { id, deviceSerial, name, trigger, priority, steps: Step[] }
Step 種類:
  tap        { x, y }                         // 正規化
  swipe      { x1,y1, x2,y2, durationMs }
  wait       { minMs, maxMs }                 // 區間=隨機(防偵測);相等=固定
  text       { value }
  key        { name: back|home|recents|... }
  waitColor  { x, y, color, tolerance, timeoutMs }
  ifColor    { x, y, color, tolerance, then: Step[], else?: Step[] }
  findTap    { template, threshold, region?, timeoutMs, offset? }   // 找圖點擊
  ifImage    { template, threshold, region?, then: Step[], else?: Step[] }
  loop       { count: number|∞, body: Step[] }
```

## UI 放置

- **裝置底下的「腳本」分頁**:該台的腳本清單 + 編輯器(步驟清單、拖曳排序、參數 + 拾取)+ 啟停 + log。取值用該台當下畫面。
- **全域「排程總覽」**:一眼看所有裝置的腳本/觸發/優先權/當前搶佔狀態 + 下次觸發。

## 執行引擎

- 直譯 JSON(迴圈/條件遞迴)。每裝置單一 runner + 搶佔器。
- 狀態(執行中/暫停/待命、當前步、迴圈計數)+ log 經 WS events(或輪詢)回報 UI。
- 每步動作後尊重 `screencap` 節流;視覺步驟輪詢到命中或逾時。

## API 與儲存

- CRUD:`/api/devices/:serial/scripts`(list/create/update/delete)。
- 執行:`POST /api/scripts/:id/run`、`/stop`;狀態 `GET`(或 WS 推播)。
- 模板/腳本存 `data/scripts.json`(+ 模板 base64 或 `data/templates/`)。排程狀態存記憶體 + 持久觸發設定。

## 風險 / 限制

- **速度**:screencap 每秒 2–5 次;快節奏不行。
- **座標脆**:優先用顏色/找圖,座標存正規化。
- **找圖不抗縮放**:模板綁解析度;多尺度是階段三。
- **CPU**:多裝置同跑要控制頻率/搜尋範圍。
- **反自動化**:部分遊戲偵測非人時序/adb input;隨機延遲只是緩解,不保證。
- **工程量大**:分階段。

## 分期

- **階段一(MVP)**:伺服器引擎 + 步驟直譯 + 動作(tap/swipe/text/key)+ **色彩比對** + **找圖點擊/若找到圖(OpenCV.js)** + `重複` + `若…(含 else)` + 手動執行 + 取值 UX(拾取/框選)+ per-device 編輯器 + 狀態/log + 儲存。
- **階段二**:排程(每日/間隔)+ 優先權搶佔 + 常駐 + 人為插手暫停/恢復 + 全域排程總覽。
- **階段三(可選)**:~~OCR~~(已做:依文字點擊/若文字含/讀取數值,含點擊座標收窄)、變數/計數器、多尺度找圖、while、進階編輯器 / JS 沙箱。

## 決策記錄

- 引擎:**伺服器端**(使用者定案)。
- 編輯器:綁裝置「腳本」分頁 + 全域排程總覽。
- 迴圈/條件:MVP 做 `重複` + `若顏色/若找到圖(含 else)`;while/變數排階段三。
- 找圖點擊:**列入 MVP**(使用者要求,視覺自動化主力)。
- OCR 引擎:**PP-OCRv6-small over ONNX**,不用 Tesseract(同一張遊戲畫面實測勝出),也不用套件內建的 v4(字典缺繁體字,實測讀不出「遊戲」「闖關」)。
- 模型發佈:**postinstall 下載 + SHA-256 驗證**,不進 git,比照 `scrcpy-server.jar`。
- 簡繁:**比對時字元級摺疊**,自產對照表,不引入 `opencc-js`(5.9MB 且多半用不到)。
- 文字點擊座標:**二分收窄實測**,不用字寬估算(估算在含圖示的行上會落在字外)。
- 多個符合:**閱讀順序 + 步驟指定第幾個**,不做隱式挑選(隱式挑選實測會選錯,且使用者看不出來)。
